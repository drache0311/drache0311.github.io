안녕하세요
요새 들어 점점 증가하는 코드량과 애매하게 나누기 어려운 도메인들이 추가되어 지금 개발에 사용중인 방법들이 여전히 유효한 지 의문이 드는 시기입니다.
의문점들을 해결하고자 얻고 싶은 목표가 생겼는데 아래와 같습니다.

1. 현재 나에게 필요한 아키텍처는 어떤 것들이 있을까?
2. 어떻게 하면 그 아키텍처를 안정적이고 유지보수가 쉽게 내가 작성할, 작성된 코드에 적용시킬 수 있을까?

이러한 목표를 해결하는데 클린 아키텍처라는 책에서 도움을 받을 수 있기를 바라며 읽게 되었습니다.
제가 좋아하는 C 일가 중 대표인 `Robert.C.Martin` 의 책으로 많은 기대가 되었습니다.
목차를 보니 `SOLID` 원칙이 절반 이상을 차지하였는데, 그동안 어렴풋으로만 알던 기본적인 원칙이 얼마나 중요하고 사고방식에 영향을 미치는 지 아직도 어렵지만 조금씩 이해가기 시작했습니다.
특히, `SRP`(Single Responsibility principle - 단일책임원칙)는 제가 원래 알고 있던 "책임을 하나만 가져야 한다" 라는 말 자체를 책에서 인용하며 잘못된 이름의 원칙으로 인한 틀린 내용이라는 것을 알게 되었을 때 꽤나 큰 충격이였습니다.
이렇듯 아직 저에게 새롭고 많이 어려운 내용이지만 읽고 이해한 내용을 적으며 정리하는 시간을 가질 수 있어 다행이라고 생각합니다.

## Single Responsibility Principal

SOLID 중 S 에 해당하는 SRP 입니다.

SRP 는 Single Responsibility principle  의 약어로써 단일책임원칙 으로 불리우고 있습니다. 하지만 책의 저자이자 원칙을 제안한 마틴은 이 이름에 대하여 부적절한 이름이라고 하였습니다.
흔히 이 원칙의 이름으로 인해 "모든 모듈은 하나의 일만 해야 한다" 라고 생각되게 되며, 실제로 구글링을 해도 같은 의미의 내용으로 설명하는 글이 상당히 많습니다.
그러나 마틴은 단 하나의 일만 해야한다는 원칙은 따로 있다고 합니다. 바로 함수는 반드시 하나의 일만 해야 한다는 원칙입니다. 이 원칙은 저수준에서 커다란 함수를 작은 함수로 리팩터링하는 원칙이며
SOLID 의 SRP 원칙에 해당되지도 않는다고 합니다. 
역사적으로 SRP 는 아래와 같이 기술되어 왔습니다.

> 단일 모듈은 변경의 이유가 단 하나, 오직 하나뿐이어야 한다.

이 설명을 보아도 아직은 애매모호합니다. 변경의 이유? 변경? 소스코드를 수정할 때의 이유인건가?
저에게는 새로운 규칙이 생겨 명확한 기준이 필요했습니다. 친절하게도 마틴은 바로 답을 알려주었습니다.
소프트웨어는 사용자와 이해관계자들을 만족시키기 위해 변경됩니다. SRP 가 말하는 `변경의 이유`란 바로 이들을 가리킵니다.
그렇다면 원칙은 아래와 같이 말할수도 있습니다

> 하나의 모듈은 하나의, 오직 하나의 사용자 또는 이해관계자에 대해서만 책임져야 한다.

추가적으로 저 사용자와 이해관계자라는 의미보다는 집단, 즉 변경을 요청하는 한 명 이상의 사람들을 `액터`라고 지칭합니다.
최종적으로 원칙은 아래와 같아집니다.

> 하나의 모듈은 하나의, 오직 하나의 액터에 대해서만 책임져야 한다. 

"액터" 라는 사용자가 등장하며 변경의 이유가 `하나의 액터에 의해서만 이루어져야 한다` 라고 합니다. 저는 변경의 주체를 기능으로만 생각했었는데 기능이 아닌
클래스를 사용하는 사용자에 두는 것입니다. 이 차이점은 원칙에 대한 해석을 완전히 뒤바꿉니다. 그리고 계속 `모듈`이라고 하는데 모듈이란 무슨 뜻인지 아시나요?
개념적으로만 알고 있었는데 책 덕분에 자신있게 말할 수 있게 되었습니다. 바로 `응집된(cohesion)` 집합입니다. 우리는 액터를 책임지는 모듈은 그렇다면 어느 범위까지라고
생각해야 할까요? 바로 이 때 응집성이 단일 액터를 책임지는 코드들을 묶어줍니다. 개발을 처음 배울 때 부터 듣던 `결합도는 낮게, 응집성은 높게`가 SRP 에도 영향을
주다니 괜히 유명한 말이 아닌듯 싶습니다.

SRP 의 위반사례를 살펴보며 이해해봅시다.

## 중복

예로 들어서 아래와 같이 `Employee` class 가 있습니다.

```java
public class Employee {

    // 초과근무 계산
    private void calculateExtraHour(){}

    // 급여 계산
    void calculatePay(){
        ...
        this.calculateExtraHour();
        ...
    }

    // 근무시간 계산
    void reportHours(){
        ...
        this.calculateExtraHour();
        ...
    }
}
```

이 클래스를 공유하는 `회계팀`, `인사팀`이라는 액터들이 있다고 가정하겠습니다.
이 클래스는 SRP 를 벌써 위반하는데, 세 가지 메서드가 서로 매우 다른 액터들을 책임지기 때문입니다.
* calculatePay 는 회계팀에서 사용합니다
* reportHours 는 인사팀에서 사용합니다

어느날 인사팀에서 초과근무를 계산하는 로직이 변경되어 `calculateExtraHour`를 변경합니다.
인사팀은 아주 만족스러워하지만, 회계팀에서는 갑자기 바뀌어버린 초과근무 계산으로 인해 급여가 변경이 되어버렸습니다.
이를 알지 못 하는 회계팀은 어디서부터 잘못된건지 찾기도 많은 시간이 소요될 것입니다.
이러한 문제는 서로 다른 액터가 의존하는 코드를 너무 가까이 배치했기 때문에 발생합니다. SRP 는 서로 다른 액터가 의존하는 코드를 서로 분리하라고 말합니다.

## 병합

서로 다른 액터를 책임지는 코드는 병합이 발생할 가능성이 확실히 더 높습니다. 두 명의 개발자가, Employee 클래스를 체크아웃 후 변경사항을 적용하면,
결과적으로 병합이 발생할 것입니다. 이 문제를 해결하는 방법도 마찬가지로 서로 다른 액터를 뒷받침하는 코드를 서로 분리시키는 것입니다.

## 해결책
이 문제들의 해결책은 다양한데, 그 모두의 공통점은 메서드를 각기 다른 클래스로 이동시키는 방법입니다.

```java
public class PayCalculator {
    EmployeeData employeeData;
    void calculatePay(){}
}
public class HourReporter {
    EmployeeData employeeData;
    void reportHours(){}
}
public class EmployeeSaver {
    EmployeeData employeeData;
    void saveEmployee(){}
}
// Data class
public class EmployeeData {}
```

각 클래스는 자신의 메서드에 반드시 필요한 소스 코드만을 포함합니다. 세 클래스는 서로의 존재를 모릅니다. 
반면, 이 해결책은 개발자가 세 가지 클래스를 인스턴스화하고 추적해야 한다는 게 단점입니다. 이럴 때 흔히 쓰는 기법으로 퍼사드(Facade) 패턴이 있습니다.

```java
public class EmployeeFacade {
    PayCalculator payCalculator;
    HourReporter hourReporter;
    EmployeeSaver employeeSaver;
    void calculatePay() {}
    void reportHours() {}
    void save() {}
}
public class PayCalculator {
    void calculatePay(){}
}
public class HourReporter {
    void reportHours(){}
}
public class EmployeeSaver {
    void saveEmployee(){}
}
// Data class
public class EmployeeData {}
```


## Conclusion
신기하게도 SRP 뿐만이 아닌 다른 개념들을 많이 알게되었습니다. 이것은 아마도 소프트웨어 원칙들과 패턴들, 개념들이 모두 같은 것을 지향하기 때문이 아닐까 싶습니다.
그동안 별개로 외워오고 별개로 적용하던 저를 돌아보는 시간이었습니다. 또는 일의 우선순위를 개발 완성을 앞세워 기본 원칙들을 어렴풋이 챙기고 뒷전으로 미루어놨던 
실수 같습니다. 앞으로 이 변하지 않을, 변화더라도 이해할 수 있도록 이 원칙과 개념들을 쌓는데 집중해야겠습니다.
